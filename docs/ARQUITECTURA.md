# Arquitectura — Galgoth Studio

Ver `docs/definiciones/galgoth-studio-mvp.md` (sección "Diseño técnico") para el diseño completo con tradeoffs — este archivo es el resumen pedagógico que se mantiene vivo conforme se implementa.

## Visión general

Monorepo con un frontend Vue 3 (editor 3D basado en Three.js) y un backend Spring Boot 4.1.0 / Java 25 (monolito modular, sin microservicios — corregido desde "3.x/Java 21" al implementar el ticket 003, ver Addendum de `docs/definiciones/galgoth-studio-mvp.md`), comunicados por REST + SSE. Postgres como base de datos (migraciones Flyway), MinIO como storage S3-compatible para imágenes/texturas/exports (todavía no levantado — se agrega cuando el ticket 024 lo necesite de verdad).

```text
Frontend (Vue3+Three.js) --REST/SSE--> Backend (Spring Boot, monolito modular)
                                          ├─ project            (proyectos/mobs)
                                          ├─ asset              (imágenes de referencia, MinIO)
                                          ├─ ai-orchestrator     (jobs de IA, SSE)
                                          ├─ model-validation    (AutoUv, FmmCompatibilityValidator)
                                          └─ export              (BBModelExporter v4/v5)
                                        --> Postgres + MinIO
```

## Estado actual

- **Frontend**: sistema de diseño base implementado (`done/002-...`) — sin pantallas productivas todavía.
- **Backend**: esqueleto real Spring Boot funcionando (`done/003-...`) — `GalgothStudioApplication` arranca, se conecta a Postgres vía `docker/docker-compose.yml` (autodetectado por `spring-boot-docker-compose`), y Flyway aplica el esquema inicial (8 tablas, ver `docs/BASE_DE_DATOS.md`). Sin Dockerfile ni deploy real todavía — sin paquetes de dominio de negocio (`project`/`asset`/`ai-orchestrator`/`model-validation`/`export`) ni ArchUnit, que aterrizan con el primer código de negocio real (ticket 005+).
- **Dominio compartido** (`done/004-...`): `MobProjectModel` -- JSON Schema (`contracts/schemas/`, fuente de verdad formal), tipos TS (`frontend/src/domain/`) y DTOs Java (`backend/.../domain/model/`), verificados por round-trip contra el mismo fixture (`contracts/fixtures/model-spec-example.json`). `CoordinateSystemContract` (`docs/adr/0001-coordinate-system-contract.md`) fija unidades/ejes/rotación/composición padre-hijo, implementado en ambos lados (`coordinateSystem.ts` / `CoordinateSystem.java`) y verificado contra el mismo fixture (`contracts/fixtures/coordinate-system-fixture.json`) — todo módulo futuro que necesite convertir coordenadas usa exclusivamente estas funciones, no reimplementa la suya.
- **Geometry Engine** (`done/005-...`, `backend/.../domain/geometry/`): whitelist cerrada de 9 operaciones (`createBone`, `createCuboid`, `resizeCuboid`, `moveCuboid`, `rotateCuboid`, `setBonePivot`, `setBoneRotation`, `parentBone`, `removeCuboid` -- master prompt §9.2), deserializadas polimórficamente por el campo `"op"` (Jackson `@JsonTypeInfo`, un valor fuera de la whitelist hace fallar la deserialización del batch completo). `GeometryEngine.apply(model, operaciones)` es una función pura y atómica: si cualquier operación falla su validación, ninguna se aplica y el modelo de entrada nunca se toca. Resuelve referencias `tempRef` (forward-refs a ids generados en el mismo batch, p.ej. un `createCuboid` que referencia el `tempId` de un `createBone` anterior) siempre a UUIDs generados por el backend, nunca a ids provistos externamente. Es el único camino por el que cualquier escritura de geometría (manual server-side o IA, tickets 018/028/031) pasa -- todo el cálculo de rotación usa `CoordinateSystem` (ticket 004), nunca una reimplementación propia. Sin endpoint REST todavía (llega con el ticket que primero lo exponga).
- **AutoUv backend** (`done/006-...`, `backend/.../domain/uv/`): `UvLayoutStrategy` (interfaz) con una única implementación este ciclo, `AlphaAutoPackStrategy` -- desenvolvimiento de caja estándar de Minecraft (shelf-packing determinista, fórmula verificada contra el código fuente real de Blockbench, no inventada) que asigna UV válida a las 6 caras de cada cuboid dentro del atlas (`MobProjectModel.uv`). `GeometryEngine.apply(model, ops, uvLayoutStrategy)` la invoca automáticamente cuando el batch incluye `createCuboid`/`resizeCuboid` -- backend es la autoridad canónica, nunca confía en la UV que ya calculó el frontend localmente. Si el conjunto de cuboids no cabe en el atlas configurado, lanza `UvAtlasOverflowException` (`UV_ATLAS_OVERFLOW`) con las dimensiones mínimas que sí lo harían caber -- el atlas nunca crece en silencio.
- **AutoUv frontend** (`done/007-...`, `frontend/src/domain/autoUv.ts`): espejo TS exacto de `AlphaAutoPackStrategy` (misma fórmula de box-UV-unwrap, mismo shelf-packing, mismo `UvAtlasOverflowError`) -- función pura y síncrona, sin ninguna petición HTTP, para feedback inmediato en el editor manual (cada `Command` de crear/redimensionar un cuboid, tickets 015-020, la llamará directo). El backend sigue siendo la autoridad canónica. Paridad verificada con una fixture compartida (`contracts/fixtures/uv-layout-fixture.json`) ejecutada en AMBOS test suites (Vitest y JUnit) -- una divergencia entre TS y Java rompe el build de cualquiera de los dos lados, no solo uno.
- **Viewport Three.js** (`done/008-...`, `frontend/src/viewport/`): `buildMobScene.ts` construye una escena PLANA a partir de un `MobProjectModel` (un mesh por cuboid, sin anidar `Object3D` por bone -- `from`/`to`/`origin` viven en un espacio compartido tipo Minecraft/Blockbench, no en el espacio local del bone padre); para cada cuboid recorre su cadena de bones ancestros y compone las rotaciones con `applyPivotRotation`/`rotationMatrixFromEulerXYZDeg` del `CoordinateSystemContract`, generalizando `composeBoneChildTransform` a N niveles. `ThreeViewportService` es el renderer/canvas ÚNICO del proceso (patrón singleton, `attachTo`/`detach` mueven el mismo canvas entre contenedores) -- sienta la base para que 016 (viewport interactivo) y 023 (thumbnails) lo reutilicen sin instanciar un `WebGLRenderer` nuevo. Development harness en `/dev/viewport-harness` (no enlazado desde la navegación productiva) abre el sample real Carcomido -- convertido UNA VEZ a `MobProjectModel` por `contracts/fixtures/scripts/convert-carcomido-sample.py` (deliberadamente NO un `BBModelImporter` de producción, ver Addendum del doc de definición) y servido como fixture estática (`contracts/fixtures/carcomido-mob-project-model.json`, copiada a `frontend/public/dev-fixtures/` para que el harness la sirva sin parsear `.bbmodel` en runtime).
- **`BBModelExporterV5`** (`done/010-...`, `backend/.../domain/export/`): exportador `.bbmodel` v5 (`meta.format_version: "5.0"`, separación `groups`/`outliner` real de Blockbench 5.0 -- verificada contra el código fuente real, no inventada). Copia directa de campos desde `MobProjectModel` (`origin`/`rotation` como `[x,y,z]`, sin transformación) per el mapeo ya fijado en el ADR 0001 -- este exportador no reinterpreta ejes/grados, solo aplica la conversión de 004. `groups[]` es un array PLANO (sin `children`); toda la jerarquía vive en `outliner` (árbol de `{uuid, isOpen, children}` para bones y uuids sueltos para cuboids hoja). El orden exacto de composición de rotación queda documentado como riesgo abierto de bajo impacto hasta que 012 lo valide contra fixtures reales de Blockbench.
- **Textura placeholder + atlas formal** (`done/011-...`): `BBModelExporterV5.export(model, uvLayoutStrategy)` (overload nuevo, el de 010 queda intacto) SIEMPRE recomputa la UV vía `AlphaAutoPackStrategy` antes de exportar -- backend es la autoridad canónica también en el punto de export, nunca confía en UV ya calculada. Genera y embebe una textura checkerboard (`PlaceholderTexture`, `java.awt.image.BufferedImage`+`ImageIO`, sin dependencia de display real) con dimensiones EXACTAS al atlas del modelo (`MobProjectModel.texture`), como data URI base64 en `textures[0]` -- el mismo índice que `Face.texture=0` ya asigna AutoUv (verificado contra `Face.getSaveCopy()` real de Blockbench: el índice referencia POSICIÓN en el array, no el campo `id`). Si el modelo no cabe en el atlas, `UvAtlasOverflowException` (006) se propaga tal cual -- el export falla explícito, nunca agranda la textura en silencio.
- **Fixtures de conformidad** (`in-process/012-...`, ⚠️ bloqueado parcialmente -- ver nota): `contracts/fixtures/model-spec-example.json` expandido con casos borde (bone y cuboid con rotación no trivial, múltiples cuboids por bone, cuboid parentado directo al bone raíz), comparado contra un snapshot aprobado a mano (`backend/src/test/resources/fixtures/bbmodel-golden/`). `carcomido_minecraft_cuboids.bbmodel` (real, del build pack) se usa como fixture de conformidad adicional vía un parser TEST-ONLY (`backend/.../export/blockbenchreal/`, nunca importado por código de producción) que prueba, de forma independiente del script Python del ticket 008, que el dominio Java puede representarlo sin pérdida. **Pendiente, bloqueado**: los archivos `.bbmodel` reales MÍNIMOS en v5 (cuboid simple/jerarquía/pivots/multi-cuboid/UV) que pide el ticket requieren exportarlos a mano desde una instalación real de Blockbench -- no disponible en este entorno. Marco los proveerá; el ticket 012 no se cierra hasta entonces.
- **`FmmCompatibilityValidator`** (`done/013-...`, `backend/.../domain/export/validation/`): valida un `.bbmodel` ya exportado (JSON válido, UUIDs únicos entre `elements`/`groups`, referencias de `outliner` resueltas, dimensiones de cuboid > 0, UV de cada cara dentro del atlas, índices de textura existentes) y reporta hallazgos específicos (`ValidationIssue{severity, rule, element, message}` -- nunca un mensaje genérico). `ValidationResult.pass()` es explícito: `true` solo si no hay ningún `ERROR` (los `WARNING` se reportan igual, no bloquean). **Corrección real encontrada al implementarlo**: la convención de nombres especiales de bone de FreeMinecraftModels que `TECHNICAL_REFERENCES.md` resumía como `hitbox`/`tag_name`/`mount_*` es imprecisa -- el código fuente real (`BoneBlueprint.java`) usa prefijos `tag_`/`b_`/`h_`/`m_` (NO `mount_`) más los nombres EXACTOS `hitbox`/`tag_name`, y estos dos últimos tienen una consecuencia real no documentada: `BoneBlueprint.generateAndWriteCubes` nunca escribe la geometría de sus cuboids hijos -- el validador lo reporta como `WARNING` (`SPECIAL_BONE_GEOMETRY_DROPPED`). `galgoth_studio_build_pack/` no se tocó (assets fuente); la corrección queda documentada aquí y en el propio ticket.
- **`BBModelExporterV4`** (`in-process/014-...`, ⚠️ parcialmente bloqueado -- misma razón que 012): exporta la MISMA geometría/jerarquía que `BBModelExporterV5` (comparten helpers vía `BBModelExportSupport`, extraído de V5 al agregar V4 para no duplicar lógica), pero sin la separación `groups`/`outliner` de Blockbench 5.0 -- cada group (bone) embebe sus datos completos directo dentro del árbol `outliner` (`BBV4OutlinerGroup`), como escribía Blockbench 4.x. `format_version: "4.10"` y la ausencia de la clave `groups` se verificaron contra el `.bbmodel` real del proyecto, igual criterio que v5. No bloquea el Gate M1 (solo exige v5); es requisito del Gate M6. **Pendiente, bloqueado** (AC #3): los mismos archivos `.bbmodel` reales mínimos v4 que pide el ticket 012 para v5 -- no se cierra hasta que Marco los provea.
- **CI**: `Jenkinsfile` en la raíz corre `buildAndTest` de frontend (lint+test+build+Sonar) y backend (`./gradlew build sonar`, incluye Testcontainers) en el mismo pipeline. **Gap conocido (ver ticket 008, sin arreglar, requiere VoBo sobre `platform`):** el pipeline solo verifica realmente el Quality Gate del ÚLTIMO análisis Sonar enviado (backend) — el del frontend nunca gatea el build aunque esté en rojo. Verificar ambos manualmente contra `sonarqube-db` en cada PR hasta que se resuelva.
