01 Resumen ejecutivo

Fase 3 agrega al Technical Alpha ya aprobado la capacidad de pintar y generar por IA la textura real de un mob, reemplazando la textura placeholder checkerboard. Cubre: un editor de textura/UV manual sobre el atlas ya calculado por AutoUv, con selección cruzada cuboid↔UV y preview 3D en vivo; integración con Draft/Command/Revision con Undo/Redo basado en patches (nunca snapshots completos del bitmap) y el bitmap persistido content-addressed con el backend como única autoridad del hash; la resolución del riesgo heredado de Fase 1+2 vía StableUvStrategy con reservas explícitas de espacio abandonado; y un pipeline de generación de textura por IA con OpenAI (modelo configurable) generando una sola imagen coherente por bone (nunca por cuboid). El exportador (BBModelExporterV5/V4) es, a partir de esta fase, un serializador puro — nunca calcula ni reempaqueta UV.

02 Alcance

Sin cambios de fondo respecto a la v1 salvo lo que las 13 correcciones tocaron explícitamente.

Incluye

  • Editor de textura/UV manual: pixel editor, regiones etiquetadas, selección cruzada cuboid↔UV, preview 3D en vivo, herramientas estándar con Undo/Redo por patches (nunca bitmap completo).
  • Import de PNG: sobre una región seleccionada, y nuevo sobre el atlas completo (crop/pad seguro, nunca deformar).
  • Resolución del atlas en dos estados nuevo: recomendada/ajustable antes de pintar (x1/x2 para Minecraft, power-of-two para custom), congelada en cuanto existe la primera región pintada.
  • StableUvStrategy con reservas/tombstones explícitos nuevo — el rect abandonado de un resize destructivo nunca vuelve a asignarse.
  • Generación de textura por IA: pipeline con OpenAI (modelo configurable), una sola imagen por bone nuevo, 4 estilos, diff obligatorio, Apply atómico nuevo.
  • El exportador nunca calcula UV nuevo — serializa exactamente la Revision; revisiones legacy se normalizan en un paso explícito previo, nunca dentro del exportador.
  • Pantallas 07 y 08 fieles al Visual Contract.

No incluye

  • Sistema de capas tipo Photoshop, generación en batch multi-mob, selección múltiple de partes simultáneas.
  • Importador de .bbmodel externos, animación, checkpoints nombrados, autenticación, responsive completo del editor, helpers FMM guiados.
  • RunPodProvider o motor de imagen local — descartado para ImageGenerationProvider.
  • Exportación de textura como archivo independiente; GC de bitmaps huérfanos/reservas en MinIO.

04 Diseño técnico

Reemplaza por completo la versión v1, tras 13 correcciones técnicas precisas del PO. Donde una corrección revierte una decisión previa, se dice explícitamente.

Hallazgo A de la v1 — REVERTIDO por decisión directa del PO

La v1 proponía que BBModelExporterV5 invocara UvLayoutSelector para decidir si recomputar UV. El PO lo rechaza explícitamente: el exportador nunca debe invocar ninguna estrategia de layout, ni siquiera sin regiones pintadas. A partir de Fase 3 el exportador es un serializador puro.

Hallazgo B — sin cambios respecto a la v1

El backend (GeometryEngine.apply vía POST /geometry/apply) sigue siendo la única autoridad para las operaciones que tocan UV. Su disparo pasa a ser exclusivamente en pointerup (§15).

1. UvRegion, UvRegionStatus y UvReservation nuevo

La corrección del PO identifica un gap real: UvRegion está indexada por (cuboidId, face) de un cuboid vivo. Cuando un resize confirmado mueve una cara pintada, el rect viejo no tiene dónde vivir — se pierde silenciosamente. Se agrega un tombstone explícito:

domain/model — UvRegion.java

public record UvRegion(String cuboidId, FaceName face, Vec4 rect, UvRegionStatus status) {}
public enum UvRegionStatus { UNPAINTED, PAINTED, ORPHAN }

/** Tombstone de espacio de atlas abandonado que ya no corresponde
 *  a ningún (cuboidId, face) vivo -- el rect que un cuboid PAINTED
 *  ocupaba antes de un resize confirmado que lo reubicó. */
public record UvReservation(
        String id, Vec4 rect, UvReservationReason reason,
        String sourceCuboidId, FaceName sourceFace) {}

public enum UvReservationReason { RESIZE_ABANDONED }

public record UvLayout(int textureWidth, int textureHeight,
        List<UvRegion> regions, List<UvReservation> reservations) {}

Un Undo (snapshot completo de MobProjectModel, ticket 019) revierte reservations igual que regions/cuboids — sin lógica adicional.

2. Resolución de estrategia UV — solo para los llamadores del motor de geometría

Sigue siendo necesaria — solo que ya NO para el exportador (§3). GeometryEngine.apply, GeometryPlannerService y AiGeometryEditPlannerService siguen decidiendo, al aplicar una operación, si el packing puede recalcularse libremente o debe preservar contenido pintado.

CasoDetecciónResultado
Resize con cara(s) PAINTED El nuevo footprint cambia una cara pintada Lanza PaintedRegionResizeConfirmationRequiredException. Confirmado: crea una UvReservation con el rect viejo, reempaqueta en espacio verdaderamente libre, marca UNPAINTED.
Add sin espacio libre No cabe en ningún espacio verdaderamente libre (regiones Y reservas) Rechaza con UvAtlasOverflowException — nunca crece ni reempaqueta.
Delete con textura pintada El cuboid tiene ≥1 cara PAINTED Sus 6 caras pasan a ORPHAN — sin crear reserva (la fila de UvRegion ya conserva el rect).

"Espacio verdaderamente libre": atlas completo menos la unión de TODAS las regiones (cualquier estado) menos la unión de TODAS las reservas. Vía manual: POST /api/mobs/{mobId}/geometry/apply (nuevo, project/api + project/geometry), disparado solo al soltar el drag (§15).

3. El exportador NO resuelve UV — reversión directa, corrección #1

BBModelExporterV4/V5 cambia su firma de export(model, uvLayoutStrategy) a export(model). Nunca invoca ninguna estrategia de layout, nunca muta el UvLayout recibido — serializa EXACTAMENTE model.uv()/model.texture(), sin excepciones. Es un cambio de firma Java interno, no un contrato externo — la API sigue devolviendo bytes idénticos para el 100% de los mobs de Fase 1+2.

Migración legacy explícita: nuevo LegacyUvNormalizationService (domain/uv), invocado por MobExportService ANTES del exportador (nunca dentro): es un no-op salvo que (a) cero regiones pintadas Y (b) el UvLayout almacenado difiera de lo que AlphaAutoPackStrategy calcularía hoy — normaliza en memoria, transitorio, nunca persistido de vuelta a la Revision inmutable.

4-5. Persistencia y dirty-check (sin cambios de fondo)

Bitmap content-addressed en MinIO (textures/{sha256}.png), nunca embebido inline. El dirty-check sigue comparando el storageKey — O(1). Único matiz: ese storageKey es siempre el que devuelve el backend (§6).

6. Integridad de storageKey — el backend es la autoridad nuevo

El frontend puede calcular SHA-256 como optimización, pero NUNCA es la fuente de verdad. En PUT /api/mobs/{mobId}/texture: el backend decodifica/valida el PNG, calcula él mismo el SHA-256, sube a MinIO, y devuelve el storageKey oficial — el cliente usa exactamente ese valor, nunca uno propio.

Flush obligatorio antes de crear una Revision: "Guardar"/"Apply" esperan la respuesta del PUT /texture pendiente antes de invocar la creación de la mob_revision. Como defensa en profundidad, el servicio que crea la Revision verifica la existencia del storageKey en MinIO antes de escribir.

7. Resolución del atlas — dos estados reescritura completa

EstadoRegla
A — antes de PAINTEDMinecraft: "x1" = lo que AlphaAutoPackStrategy calcula para esa geometría; "x2" = upgrade explícito, doble resolución lineal, mismo layout. Custom: potencia de 2 superior al footprint real. Si no cabe, upgrade explícito — nunca crecimiento silencioso.
B — después de PAINTEDwidth/height quedan CONGELADOS. StableUvStrategy nunca crece el atlas. Si no cabe una región nueva → UvAtlasOverflowException.

La transición A→B es unidireccional dentro de un mismo ciclo de vida del mob.

8. Importación de PNG — región y atlas completo nuevo

Atlas completo con dimensiones exactas: confirmación/diff. Dimensiones distintas: ÚNICAMENTE crop y/o pad — nunca escalado (viola el canvas pixel-perfect ya aprobado). Nunca se deforma sin confirmación explícita. Una única operación de Undo por import.

9. Undo/Redo de textura — TexturePatchCommand reescritura completa

frontend/src/editor/texture — TexturePatchCommand.ts

interface TexturePatchCommand {
  rect: { x: number; y: number; width: number; height: number }
  beforePixels: Uint8ClampedArray  // solo los píxeles de rect, ANTES
  afterPixels: Uint8ClampedArray   // solo los píxeles de rect, DESPUÉS
}

Brush/erase: rect = bounding box del trazo completo (pointerdown→pointerup), no por evento intermedio. Fill: bounding box de la región rellenada. Apply de IA: unión de los atlasUvRect tocados por esa generación — un Apply = un Command, sin importar cuántos slices involucró. Undo/Redo son O(área del rect), nunca O(atlas completo).

10. Atomicidad del Apply de textura nuevo

Apply deja siempre uno de dos estados: todo aplicado, o nada. Orden: (1) flush de MinIO PRIMERO, fuera de la transacción — seguro porque la clave es el hash del contenido; (2) UNA transacción Postgres que actualiza mob_drafts, inserta mob_revisions, y actualiza current_revision_number — todo o nada. Reject no toca ninguno.

Nota de diseño: esto diverge deliberadamente del Apply de geometría existente (que solo toca el draft, la Revision se crea después en un "Guardar" separado) — la corrección del PO pide explícitamente que Apply de TEXTURA cree la Revision en el mismo movimiento. Intencional, no una inconsistencia.

11. Generación de textura por IA — TextureGenerationSheet por bone reescritura completa, cambia la estrategia principal

La v1 emitía una llamada por CUBOID (nunca implementada, sin VoBo, sin código escrito) — se reemplaza directamente. El problema real: cada cuboid podía salir con estilo/paleta distintos al venir de llamadas independientes.

Nueva forma: TexturePlan global (Claude) → TextureGenerationSheet por bone → ImageGenerationProvider → UNA imagen temporal con TODAS las caras del bone → slicing determinista (TextureSheetSlicer) → TextureCompositorService → atlas.

aiorchestrator/texture — TextureGenerationSheet.java

public record TextureGenerationSheet(
    String boneId, String boneName,
    List<CuboidFacePlacement> placements,
    String semanticLabel, String dominantPalette, String materialNotes,
    String referenceImageId, int sheetWidth, int sheetHeight) {}

public record CuboidFacePlacement(
    String cuboidId, FaceName face,
    Vec4 sheetRect,      // posición dentro de la imagen temporal
    Vec4 atlasUvRect,    // destino real del slicing en el atlas
    Vec3 relativeSize, String orientationHint) {}

UNA sola llamada de imagen por bone cuando es técnicamente posible. Fallback/batching explícito (nunca el camino por defecto): si el bone excede los límites del modelo configurado, se divide en N sub-sheets, cada una visible en el SSE (generando_bone_X (parte 2/3)).

12. Modelo de OpenAI configurable nuevo

application.properties

ai.openai.api-key=${OPENAI_API_KEY:}
ai.openai.image-model=${OPENAI_IMAGE_MODEL:gpt-image-1}

Ningún literal hardcodeado en dominio/lógica de negocio. ai_jobs.model registra el valor REAL usado en cada llamada — nunca un literal fijo en el código.

13. SSE — esquema formal de preview_texture_patch formalizado

type PreviewTexturePatchEvent = {
  type: 'preview_texture_patch'
  rect: { x: number; y: number; width: number; height: number }
} & (
  | { encoding: 'base64'; data: string }   // parche pequeño, inline
  | { encoding: 'asset_url'; url: string } // parche grande, asset temporal
)

Umbral: 32 KB de payload base64 (~24 KB de PNG crudo). Por debajo, inline; por encima, asset temporal en MinIO. Estos previews NUNCA se persisten como textura definitiva.

14. Selección de cara determinista reescritura completa

La v1 dependía de intersection.face.normal como mecanismo primario — se invierte. Cada BoxGeometry etiqueta mesh.userData.faceNamesByGroup: FaceName[6] en su construcción, resuelto desde CoordinateSystemContract. pickCuboidFaceAt usa intersection.face.materialIndex para indexar directamente — determinista, sin calcular nada. La normal queda solo como validación/fallback en dev.

15. Resize manual — preview local en pointermove, commit único en pointerup nuevo

POST /geometry/apply NO se llama en cada frame del drag. Durante pointermove: preview 100% local, sin llamada al backend. Solo al pointerup se envía la operación canónica. Si el backend responde con la excepción de confirmación, el frontend mantiene el preview visual del tamaño soltado y muestra el diálogo — "Confirmar" reenvía con confirmPaintLoss: true.

16-18. Conflicto 409, compatibilidad legacy, y tablas Postgres (sin cambios de fondo)

El chequeo de 409 (base_revision_number/base_draft_version) corre ANTES del flujo de atomicidad del §10. Revisiones legacy deserializan con default UNPAINTED y reservations=[]. Única columna nueva: ai_jobs.target_bone_id (nullable) + nuevos job_type.

20. Pregunta abierta genuina de esta revisión

La única interpretación que de verdad requiere al PO: la semántica exacta de "x1/x2" para presets Minecraft (§7) — este diseño asume "x1" = dimensión calculada por AlphaAutoPackStrategy para la geometría real (no una tabla fija por especie vanilla, concepto que el dominio no modela hoy). Ver Riesgos #1.

        no hay GC este ciclo, y ese rect NUNCA
        vuelve a asignarse.
    end note

    note left of UNPAINTED
        Una UvReservation tambien cuenta como
        "ocupado" para Add/resize futuros -- el
        espacio verdaderamente libre excluye
        regiones activas Y reservas/tombstones.
    end note

    UNPAINTED --> ORPHAN: delete del cuboid dueño\n(bloque completo de sus 6 caras)
    PAINTED --> ORPHAN: delete del cuboid dueño\n(bloque completo de sus 6 caras)

    ORPHAN --> [*]: terminal este ciclo\n(sin GC ni reclamo de espacio)

    note right of ORPHAN
        Unica forma de revivir el contenido:
        un Undo que restaura el MobProjectModel
        COMPLETO de antes del delete -- no es
        una transicion de estado hacia adelante.
    end note

Diagrama central: cada cara tiene uno de 3 estados. La transición hacia atrás (PAINTED → UNPAINTED) no limpia nada — mueve la cara y deja una UvReservation explícita que nunca vuelve a asignarse este ciclo.
