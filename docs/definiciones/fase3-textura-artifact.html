Fase 3 — Editor de textura/UV y generación de textura por IA

Reemplaza la textura placeholder del Technical Alpha por arte real: pintado a mano sobre el atlas, generación por IA con OpenAI, y una estrategia de UV estable que protege el trabajo pintado de cambios posteriores de geometría.

01 Resumen ejecutivo

Fase 3 agrega al Technical Alpha ya aprobado la capacidad de pintar y generar por IA la textura real de un mob, reemplazando la textura placeholder checkerboard que hoy garantiza únicamente que el export sea válido. Cubre: un editor de textura/UV manual tipo pixel-art sobre el atlas ya calculado por AutoUv, con selección cruzada cuboid↔UV y preview 3D en vivo; la integración de ese trabajo con el sistema ya existente de Draft/Command/Revision sin duplicar bitmaps completos por trazo; la resolución del riesgo abierto heredado de Fase 1+2 sobre una UV que ya no puede reempaquetarse libremente porque tiene textura pintada encima (vía una StableUvStrategy nueva); y un pipeline de generación de textura por IA usando OpenAI (gpt-image-1) como ImageGenerationProvider, con el mismo patrón «IA propone, la app valida y aplica con diff» ya probado en geometría (ticket 031).

02 Objetivo de negocio

El Technical Alpha entrega geometría editable con textura placeholder — suficiente para validar el pipeline determinista de modelo 3D, pero insuficiente como producto usable: un mob sin textura real no es un mob terminado para un servidor de Minecraft. Fase 3 cierra esa brecha, permitiendo que el flujo completo (referencia → geometría por IA → textura por IA/manual → export) produzca un .bbmodel con arte real, listo para usarse, sin salir de Galgoth Studio ni depender de Blockbench para la parte de pintado.

Usuarios / roles involucrados

Sin cambios respecto a Fase 1+2: creador de contenido para Minecraft (usuario principal) y usuario avanzado/editor manual — la misma persona, ahora también pintando/generando textura. Sigue sin roles de colaboración, permisos ni autenticación.

03 Alcance

Qué construye esta fase y qué queda explícitamente fuera — incluye 6 decisiones que ya tomó el Product Owner el 9 sep 2026.

Incluye

  • Editor de textura/UV manual: pixel editor sobre el atlas, regiones UV etiquetadas por parte del cuerpo/cara, selección cruzada cuboid↔UV, preview 3D en vivo, herramientas estándar (color picker/paleta, brush, eraser, fill bucket, eyedropper, selection, copy/paste con crop/fit, undo/redo, grid toggle).
  • Persistencia y revisiones de textura: integrada con el Draft/Revision ya existente; bitmap persistido content-addressed en MinIO, nunca embebido inline en el JSON del modelo.
  • StableUvStrategy: protege regiones UV ya pintadas frente a resize/add/delete de cuboids.
  • Generación de textura por IA: pipeline completo con OpenAI (gpt-image-1), 4 estilos, regeneración por bone, diff Antes/Después obligatorio.
  • Pantallas 07 y 08 (editor de textura, generador IA de textura) fieles al Visual Contract ya vigente.
  • Flujo end-to-end: pintar/generar → ver en 3D → Guardar → exportar con textura real → abre en Blockbench sin reparación.

No incluye

  • Sistema de capas tipo Photoshop — una sola superficie editable por mob.
  • Generación en batch para múltiples mobs, o selección múltiple de partes simultáneas.
  • Importador de .bbmodel externos, sistema de animación, checkpoints nombrados, autenticación/multi-tenencia, responsive completo del editor, helpers de autoría FMM guiados — todo sigue fuera, mismo criterio de Fase 1+2.
  • RunPodProvider o motor de imagen local/self-hosted — descartado explícitamente para ImageGenerationProvider este ciclo.
  • Exportación de la textura como asset independiente fuera del paquete ya definido en Fase 1+2.
  • GC de bitmaps huérfanos en MinIO — sin política de poda este ciclo.
6 decisiones del Product Owner · 9 sep 2026
  • Resize con textura pintada → avisar y pedir confirmación explícita, nunca silencioso ni automático.
  • Atlas lleno + regiones pintadas → rechazar la creación con error explícito, nunca crecer el atlas.
  • Delete de cuboid pintado → la región queda huérfana, reservada, no reutilizable este ciclo.
  • Imagen de OpenAI fuera de límite → recorte/escala automático, sin reintento ni error.
  • Estilos de generación → 4 opciones, fiel al mockup 08 (incluye «Realista»).
  • Granularidad de regeneración → por bone completo, no por cara individual.

05 Diseño técnico

Decisiones de architect, con tradeoffs explícitos donde hubo más de una opción razonable.

Hallazgo A — exportador recomputaba UV siempre

BBModelExporterV5.export(model, uvLayoutStrategy) siempre recomputa la UV desde cero vía AlphaAutoPackStrategy antes de exportar. Correcto en Fase 1+2 (sin textura pintada, recomputar es determinista); destructivo en Fase 3, donde volvería a empaquetar el atlas ignorando dónde está el arte real. Se resuelve abajo, §2.

Hallazgo B — el editor manual nunca revalida UV en el backend

El editor manual (018/036) calcula AutoUv 100% client-side; el backend nunca lo revalida en autosave/Guardar. Inocuo en Fase 1+2 (el export siempre recomputaba); en Fase 3, con StableUvStrategy protegiendo regiones pintadas, un cliente que calcule su propia UV localmente podría saltarse esa protección. Se resuelve abajo, §2.

1. Extensión de MobProjectModel

TextureDocument(int width, int height, String storageKey) no cambia de forma — solo de semántica: storageKey pasa a ser la clave real, content-addressed, de la textura pintada. UvRegion gana un campo de estado:

domain/uv — UvRegion.java

public record UvRegion(String cuboidId, FaceName face, Vec4 rect, UvRegionStatus status) {}

public enum UvRegionStatus { UNPAINTED, PAINTED, ORPHAN }
  • UNPAINTED — región de un cuboid/cara vivo sin arte real todavía.
  • PAINTED — región con al menos un píxel editado por el usuario o compuesto por IA. Flag explícito actualizado en el mismo commit que pinta — no derivado por diff de píxeles.
  • ORPHAN — tombstone de una región cuyo cuboid ya no existe, tras un delete.

2. Contrato StableUvStrategy

UvLayoutStrategy.layout(cuboids, w, h) no puede saber qué regiones están pintadas. Se resuelve con extensión aditiva — un método default nuevo que preserva 100% compatibilidad con AlphaAutoPackStrategy:

domain/uv — UvLayoutStrategy.java

public interface UvLayoutStrategy {
    Result layout(List<Cuboid> cuboids, int textureWidth, int textureHeight); // sin cambios

    default Result layout(List<Cuboid> cuboids, int textureWidth, int textureHeight,
                           List<UvRegion> previousRegions) {
        return layout(cuboids, textureWidth, textureHeight); // default: reflow completo
    }
}

UvLayoutSelector implements UvLayoutStrategy (nuevo, marcado @Primary) se inyecta en todos los puntos que hoy reciben UvLayoutStrategy (GeometryEngine.apply, GeometryPlannerService, AiGeometryEditPlannerService, BBModelExporterV5): sin ningún PAINTED/ORPHAN previo delega en AlphaAutoPackStrategy (byte-idéntico a Fase 1+2); con al menos uno, delega en StableUvStrategy. Ambas comparten la matemática de box-unwrap ya verificada, extraída a un helper común BoxUvMath.

Vía manual vs. vía IA — ninguna se salta la protección. Vía IA (031): si GeometryEngine.apply dispara la excepción, se refleja en el diff como «N caras perderán su arte» — el botón «Aplicar cambios» ya sirve como confirmación. Vía manual (018/036): se agrega POST /api/mobs/{mobId}/geometry/apply (nuevo MobGeometryController en project/api/, respaldado por project/geometry/ — mismo patrón que project/draft/DraftPersistenceService) solo para createCuboid/resizeCuboid/removeCuboid; moveCuboid/rotateCuboid/pivot siguen 100% client-side, sin regresión de latencia en el drag. Si el backend devuelve la excepción, el frontend muestra el modal y reenvía con confirmPaintLoss: true.

Cierra el Hallazgo A: BBModelExporterV5 invoca UvLayoutSelector en vez de AlphaAutoPackStrategy directo — idéntico a hoy sin regiones pintadas; con ellas, exporta la UV tal cual está almacenada, sin recomputar.

3. Persistencia eficiente de textura en revisiones

Decisión: bitmap content-addressed en MinIO. Clave textures/{sha256-hex}.png, global — el hash desambigua y permite dedup incluso entre mobs distintos. TextureDocument.storageKey guarda esa clave; el bitmap nunca se embebe inline en model_jsonb.

Se descarta diffs binarios por región: cada mob_revisions es hoy un snapshot completo e independiente — introducir deltas rompería esa auto-contención. Efecto directo: dos revisiones sin cambio de bitmap comparten storageKey — dedup automático y gratuito. El editor de píxeles (Web Worker/OffscreenCanvas) exporta el bitmap, calcula SHA-256 (Web Crypto) y lo sube vía PUT /api/mobs/{mobId}/texture — el backend sube a MinIO solo si la clave no existe (idempotente).

4. Dirty-check/autosave para textura

Decisión: valor completo del MobProjectModel, sin caso especial. Como storageKey ya es un hash de contenido, el .equals() estructural que DraftPersistenceService ya usa compara strings de clave — O(1), sin checksum nuevo.

5. OpenAiImageProvider

ImageGenerationProvider se extiende de forma aditiva:

aiorchestrator/provider — ImageGenerationProvider.java

public interface ImageGenerationProvider {
    byte[] generateImage(String prompt); // se conserva

    byte[] generateTextureRegion(TextureGenerationRequest request);

    record TextureGenerationRequest(
        String prompt, byte[] referenceImageBytes,
        int targetWidth, int targetHeight, String style) {}
}

OpenAiImageProvider (nuevo, aiorchestrator/provider/) usa gpt-image-1 vía POST /v1/images/edits cuando hay región existente que preservar/inpaintear, o /v1/images/generations para la primera pasada. Verificar el identificador de modelo vigente contra la documentación real de OpenAI al implementar.

Split de responsabilidades («IA propone, la app valida y aplica»):

  1. Paleta + mapeo semántico — StructuredReasoningProvider (Claude), paso separado antes de OpenAI. Nueva salida validada TexturePlan (mismo patrón que ModelIntent): etiqueta semántica por bone, paleta dominante/acento, notas de material.
  2. Resolución determinista de layout — 100% código. Granularidad = bone; un bone con varios cuboids emite una llamada por cuboid, agrupadas bajo un único paso de progreso.
  3. Composición de prompt — código determinista: estilo + etiqueta semántica + paleta + orientación de cara.
  4. Llamada a OpenAI → bytes PNG crudos.
  5. TextureCompositorService (nuevo, aiorchestrator/texture/) — determinista: recorta/escala si no calza, compone sobre una copia del atlas (nunca sobre el bitmap en vivo), corre limpieza de píxeles/paleta para Pixel Art/Minecraft Vanilla.
  6. ai_jobs bookkeeping — nuevos job_type, mismo esquema (provider='openai', model, prompt/schema version, reference IDs).

6. Progreso vía SSE

Reutiliza ai_job_events/SSE tal cual (replay por Last-Event-ID) — nuevos valores de stage (analizando_paleta, mapeando_caras, generando_bone_X, componiendo_atlas, limpiando_pixeles). Cada evento lleva un preview_texture_patch (parche + rect, no el atlas completo).

7. Selección de cara individual

ThreeViewportService.pickCuboidIdAt raycastea contra el mesh completo — sin tagging por cara. Se extiende de forma aditiva usando intersection.face.normal (nativo del raycast), mapeada a NORTH/SOUTH/EAST/WEST/UP/DOWN vía el CoordinateSystemContract ya existente. Nueva función pickCuboidFaceAt; la selección vive en textureSelectionStore.ts, separado del store de selección de cuboid completo.

8. Alcance del Undo/Redo de textura

Decisión: pila independiente por tab. Un trazo de pincel puede tocar miles de píxeles — snapshotear el bitmap completo en la misma pila que geometría sería órdenes de magnitud más pesado. Los tabs Modelo/Textura son la frontera natural.

9. Conflicto 409 al aplicar textura

Decisión: contra cualquier avance del draft compartido, no solo textura — geometría y textura viven en el mismo MobProjectModel. Se reutiliza literalmente el chequeo ya implementado en AiEditService.applyEdit.

10. textureResolution del wizard vs. atlas real

Decisión: se reemplaza por un valor derivado del atlas. El tamaño real lo determina el packing de la geometría real, que ocurre después de que el wizard pide ese campo — mantenerlo vinculante reintroduciría dos fuentes de verdad. Se quita como parámetro enviado al backend; el atlas sigue el default de 128×128 y crece/rechaza según la geometría real.

11. Compatibilidad con revisiones existentes

Las filas viejas tienen uv.regions[].status ausente y texture.storageKey = null. Se resuelve sin migración: UvRegion.status deserializa con default UNPAINTED cuando falta — un modelo viejo cae en la rama AlphaAutoPackStrategy, comportamiento idéntico a hoy. Se agrega un test de regresión con una fixture real de Fase 1+2.

12. Nuevas tablas/columnas Postgres

Cambio relacional mínimo — texture/UV viven dentro del model_jsonb ya existente:

V3__ai_jobs_texture_job_types.sql

alter table ai_jobs drop constraint ai_jobs_job_type_check;
alter table ai_jobs add constraint ai_jobs_job_type_check
    check (job_type in ('generate', 'edit', 'generate_texture', 'edit_texture'));

alter table ai_jobs add column target_bone_id text; -- nullable

Deliberadamente sin tabla nueva para bitmaps (MinIO ya es la fuente de verdad, content-addressed) ni para huérfanas (viven dentro de uv.regions del JSONB).

13. Pendiente de ticket, no bloquea VoBo

Formatos de imagen adicionales, límites de tamaño/resolución de textura, cuotas/rate-limiting de OpenAI, moderación de contenido — mismo criterio que los riesgos análogos de Fase 1+2.

        Si no cabe en espacio verdaderamente
        libre, error de rechazo (nunca crece
        el atlas ni reempaqueta para hacerle sitio).
    end note

    UNPAINTED --> PAINTED: usuario pinta a mano,\no Apply de generación IA sobre esta cara

    PAINTED --> UNPAINTED: resize confirmado\n(confirmPaintLoss=true)
    note right of PAINTED
        La cara se reempaqueta en espacio LIBRE
        nuevo y queda UNPAINTED ahi. El bitmap
        viejo, en su posicion original, queda
        como garbage aceptado, no se re-visita,
        no hay GC este ciclo.
    end note

    UNPAINTED --> ORPHAN: delete del cuboid dueño\n(bloque completo de sus 6 caras)
    PAINTED --> ORPHAN: delete del cuboid dueño\n(bloque completo de sus 6 caras)

    ORPHAN --> [*]: terminal este ciclo\n(sin GC ni reclamo de espacio)

    note right of ORPHAN
        Unica forma de revivir el contenido:
        un Undo que restaura el MobProjectModel
        COMPLETO de antes del delete (snapshot
        de ticket 019), no es una transicion
        de estado hacia adelante de ORPHAN.
    end note

El diagrama central del documento: cada cara de cada cuboid vivo tiene uno de estos 3 estados. La única transición hacia atrás (PAINTED → UNPAINTED) no limpia nada — mueve la cara a una ubicación nueva y abandona el bitmap viejo como basura permanente. ORPHAN es una trampa de un solo sentido: la salida es un Undo que reemplaza todo el modelo, no una transición hacia adelante.

Secuencia — resize con confirmación (vía manual)

sequenceDiagram
    autonumber
    actor U as Usuario
    participant ED as Editor (frontend)
    participant API as POST /geometry/apply
    participant ENGINE as GeometryEngine.apply
    participant SEL as UvLayoutSelector

    note over U,ED: Move/Rotate NO pasan por este flujo, siguen 100% client-side + autosave (018)

    U->>ED: arrastra handle de resize del cuboid
    ED->>API: POST geometry/apply { op: resize, ... }
    API->>ENGINE: apply(operation)
    ENGINE->>SEL: resuelve estrategia UV
    SEL-->>ENGINE: previousRegions tiene PAINTED/ORPHAN -> StableUvStrategy
    ENGINE->>ENGINE: detecta caras PAINTED afectadas por el nuevo tamaño
    ENGINE-->>API: throw PaintedRegionResizeConfirmationRequiredException
    API-->>ED: 4xx con detalle de que caras se perderian

    ED->>U: modal de confirmacion

    alt Usuario cancela
        U->>ED: Cancelar
        note over ED: nada se reenvia, cuboid vuelve al tamaño anterior
    else Usuario confirma
        U->>ED: Confirmar
        ED->>API: POST geometry/apply (MISMA operacion) confirmPaintLoss=true
        API->>ENGINE: apply(operation, confirmPaintLoss=true)
        ENGINE->>SEL: resuelve estrategia UV (mismo resultado)
        SEL-->>ENGINE: StableUvStrategy
        ENGINE->>ENGINE: reempaqueta caras afectadas en espacio libre, marca UNPAINTED
        ENGINE-->>API: geometria + UV aplicados
        API-->>ED: 200 OK
        ED->>U: refleja el resize + reset visual en esas caras
    end

El mismo endpoint y la misma excepción cubren Add/Remove — se dibuja Resize por ser el único con una rama de confirmación explícita. Add nunca pisa una región pintada por diseño; Remove no requiere confirmación porque el usuario ya sabe que borra el cuboid completo.

  • Control de contenido/moderación sobre las imágenes generadas por OpenAI.
