# 054 — Pipeline completo de generación de textura por IA: SSE + diff + Apply atómico + 409

**Milestone:** M9 · **Depende de:** 045, 051, 052, 053 · **HUs:** HU-36, HU-37, HU-38, HU-39 · **Épica:** M (`docs/definiciones/galgoth-studio-fase3-textura.md`)

## Objetivo
Nace de `docs/definiciones/galgoth-studio-fase3-textura.md` (Diseño técnico §6/§10/§13/§16). Orquesta el pipeline end-to-end de generación/regeneración de textura por IA: `TexturePlan` → `TextureGenerationSheet` por bone → generación → slicing/composición → progreso SSE con el esquema formal de `preview_texture_patch` → diff Antes/Después → Apply (atómico, con conflicto 409) / Reject.

## Criterios de aceptación (TDD)
- Dado que el usuario elige estilo (1 de 4: Fiel a la referencia / Minecraft Vanilla / Pixel Art / Realista), nivel de detalle, y opcionalmente un `boneId`, cuando confirma la generación, entonces se dispara el pipeline completo reutilizando la imagen de referencia ya subida en Fase 2 — nunca pide una nueva.
- Dado el pipeline corriendo, cuando reporta progreso, entonces reutiliza `ai_job_events`/SSE existente con los nuevos valores de `stage` (`analizando_paleta`, `mapeando_caras`, `generando_bone_X`, `componiendo_atlas`, `limpiando_pixeles`).
- Dado un evento `preview_texture_patch`, cuando se emite, entonces cumple el esquema `{ type, rect, encoding: 'base64'|'asset_url', data|url }` — payloads de hasta 32 KB en base64 van inline; por encima, como asset temporal en MinIO. Estos previews NUNCA se persisten como textura definitiva (test que confirma que ningún preview toca `mob_drafts`/`mob_revisions`/`textures/{hash}.png` fuera de un Apply real).
- Dado que el pipeline termina, cuando se presenta el resultado, entonces se muestra como una PROPUESTA con diff Antes/Después (región afectada, o atlas completo si fue "Modelo completo") — con Apply/Reject explícitos.
- Dado Reject, cuando se ejecuta, entonces no modifica ni el draft ni ninguna revisión.
- Dado Apply, cuando se invoca, entonces primero verifica conflicto: si CUALQUIER parte del draft/revisión compartido (geometría O textura) avanzó desde que se generó la propuesta, responde 409 y descarta la propuesta sin tocar nada.
- Dado Apply SIN conflicto, cuando se ejecuta, entonces actualiza de forma ATÓMICA: (1) sube el bitmap a MinIO PRIMERO, fuera de la transacción de base de datos; (2) UNA transacción Postgres que actualiza `mob_drafts`, inserta `mob_revisions` (texture+geometría juntas) y actualiza `current_revision_number` — todo o nada (test de integración que fuerza un fallo a mitad de la transacción y confirma que NINGUNA fila queda escrita a medias).
- Dado un Apply exitoso, cuando se hace un `GET` posterior del draft/modelo, entonces se obtiene EXACTAMENTE la textura aplicada — nunca un estado intermedio.
- Dado la migración `V3__ai_jobs_texture_job_types.sql`, cuando se aplica, entonces `ai_jobs` acepta `job_type` `generate_texture`/`edit_texture` y persiste `target_bone_id` (nullable) para regeneraciones de un bone específico.
- Dado que un bone regenerado tenía contenido pintado a mano, cuando se genera el diff, entonces señala explícitamente que se sobrescribirá contenido pintado a mano — no solo contenido generado previamente por IA.

## Hecho

Implementado en la rama `feature/054-pipeline-ia-sse-diff-apply-atomico`.

**Nuevo:** `TextureGenerationService` (`backend/.../aiorchestrator/texture/`), orquestador end-to-end -- mismo patrón que `MobGenerationService` (028/029): `startGeneration` síncrono hasta crear la fila `ai_jobs` (`job_type=generate_texture` si `boneId` es `null`/ausente -- HU-36 todos los bones con geometría; `job_type=edit_texture` si viene poblado -- HU-37 un bone puntual), pipeline real en `generationExecutor`. Por cada bone objetivo: `TexturePlanService.analyze` (052) → `TextureGenerationSheetPlanner.plan` (053) → por cada sheet/parte: `ImageGenerationProvider.generateTextureSheet` (051) → `TextureSheetSlicer.slice` + `TextureCompositorService.compose` (053), acumulando sobre una copia en memoria del atlas. `TextureGenerationController` expone `POST /api/mobs/{mobId}/ai/generate-texture`, `GET /api/jobs/{jobId}/texture-result`, `POST /api/jobs/{jobId}/apply-texture`; `GET /api/jobs/{jobId}/events` (029) se reutiliza sin tocarlo. `TexturePreviewAssetController` sirve los assets temporales de `preview_texture_patch` cuando exceden 32 KB.

**Hallazgos reales reportados explícitamente (sin parches silenciosos, ver también `docs/ARQUITECTURA.md`):**
1. **`chk_ai_jobs_base_values_by_type` (003) necesitó actualizarse más allá de lo que el ticket pedía literalmente** -- `generate_texture`/`edit_texture` siempre corren sobre un mob con `revision_number >= 1`, así que necesitan `base_revision_number`/`base_draft_version` `NOT NULL` (mismo criterio que `edit`) para que el chequeo 409 tenga contra qué comparar. Documentado en el propio comentario de la migración V3.
2. **El Diseño técnico §10 tiene una premisa desactualizada**: describe el Apply de textura como una "divergencia deliberada" del Apply de geometría porque asume que este último "SOLO actualiza el draft -- la Revision se crea después, en un Guardar separado". Verificado contra el código real: `DraftPersistenceService.applyGenerationProposal` (ya existente desde el ticket 030) YA actualiza `mob_drafts` + inserta `mob_revisions` + avanza `current_revision_number` en UNA sola transacción -- exactamente lo que este ticket necesitaba, reutilizado sin ningún cambio de comportamiento. No hay ninguna divergencia real entre ambos flujos de Apply. Recomendación: corregir esa premisa en `docs/definiciones/galgoth-studio-fase3-textura.md` en la próxima revisión del documento.
3. **`ImageGenerationProvider` (051) necesitó una extensión aditiva no anticipada**: `generateTextureSheet` devuelve solo `byte[]`, sin forma de que el orquestador sepa qué proveedor/modelo REAL usar en `ai_jobs` (HU-39) sin un `instanceof` frágil. Se agregaron `provider()`/`model()` a la interfaz, implementados por `OpenAiImageProvider` (`model()` ya existía desde 051, ahora `@Override`) y `MockImageProvider`.
4. **Ni el Diseño técnico ni el ticket fijan CÓMO distinguir "pintado a mano" de "generado por IA"** (AC #8) -- hasta este ticket, `UvRegionStatus.PAINTED` (040) no lleva información de origen. Se agregó `UvPaintOrigin`/`UvRegion.paintedBy` de forma aditiva (mismo mecanismo que `status`), con default conservador (`null` → tratado como posible pintado a mano). Contratos espejo actualizados (`contracts/schemas/mob-project-model.schema.json`, `frontend/src/domain/MobProjectModel.ts`). **Gap explícito para un ticket futuro**: el editor de pintado manual (047) no escribe `paintedBy=hand` todavía -- el default conservador ya cubre la corrección del AC sin eso, pero la auditoría quedaría más completa si el editor lo escribiera explícitamente.
5. **"Limpieza de píxeles/paleta" (stage `limpiando_pixeles`)**: se emite el stage (satisface el AC de que la SSE exponga ese valor), pero sin una transformación de post-procesado real -- el aislamiento espacial de 053 ya deja el atlas compuesto sin nada que "limpiar" que ningún AC concreto de este ticket exija verificar. Documentado como simplificación deliberada, no un olvido.

**Mejora continua propuesta:** un hook/skill que, al agregar una columna/constraint nueva a una migración Flyway, recuerde revisar TODAS las constraints existentes de la tabla tocada (no solo la que el ticket menciona explícitamente) habría anticipado el hallazgo #1 sin necesidad de que el test de schema lo descubriera en la primera corrida.
