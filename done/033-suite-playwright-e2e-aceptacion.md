# 033 — Suite Playwright del flujo E2E de aceptación

**Milestone:** M6 · **Depende de:** 020, 030, 031, 032, 014 · **HUs:** HU-23

## Objetivo
Nace de `docs/definiciones/galgoth-studio-mvp.md` (HU-23, criterios de aceptación núm. 1-12 del master prompt). Automatizar el flujo E2E completo del Technical Alpha: crear proyecto Galgoth → agregar mob Carcomido → generar geometría por IA → Usar este modelo → editar a mano y Guardar → editar por IA con diff y Apply → validar → exportar `.bbmodel` (v5, y v4 vía 014) → abrir en Blockbench sin diálogos de reparación.

## Criterios de aceptación (TDD)
- Dado el flujo completo descrito arriba, cuando corre la suite Playwright, entonces cada paso pasa contra un backend real (Docker Compose) con `MockProvider` (025) para las llamadas de IA.
- Dado el `.bbmodel` resultante (v5 y v4), cuando se valida contra las fixtures de Blockbench real (012), entonces ambos abren sin diálogo de reparación.
- Dado que la suite corre en CI, cuando termina, entonces reporta verde antes de considerar cerrado el Technical Alpha (Gate M6) — incluyendo que 014 (V4) esté completo, como exige el Gate M6 de la épica 009. **(No logrado -- ver `## Hecho`: el PO aceptó explícitamente este gap como riesgo conocido en vez de bloquear el cierre del ticket por él.)**

**AC #2, mitad v4 -- decisión confirmada explícitamente con el PO**: el producto real (032) nunca expuso una opción de exportar en v4 (ni mockup ni endpoint -- V4 es una capacidad interna de compatibilidad con FreeMinecraftModels, 014), así que ningún paso de navegador puede ejercerla. **AC #2, "abren sin diálogo de reparación"**: ya demostrado con Blockbench real al cerrar 009/012/014 (mismo exportador, mismo código -- ver el `## Hecho` de esos tickets) -- no se repite acá.

**Cuatro hallazgos reales, solo detectables al ejercitar el flujo COMPLETO de punta a punta (nunca con los tests unitarios/integración existentes, cada uno mockeaba/aislaba su propio escenario)**:
1. `MockReasoningProvider` (025) tenía un ÚNICO default literal (el ejemplo de EDICIÓN del master prompt §9.3) compartido por los dos llamadores reales de la interfaz -- generación (sobre un modelo VACÍO) y edición (sobre un modelo YA existente). Un servidor real recién levantado sin ningún test que llamara `setNextResponse` habría fallado el paso de generación de verdad (`resizeCuboid` sobre un target que no existe en un modelo vacío). Fix: dos defaults, elegidos por `promptVersion`.
2. Aun separados, el default de edición seguía apuntando a ids LITERALES (`hand_right`/`hand_left`/`shoulder_right_detail`) que solo existen en el fixture armado a mano de `AiGeometryEditPlannerServiceTest` (031) -- `GeometryEngine.applyCreateCuboid` SIEMPRE asigna un UUID nuevo al crear (nunca el `tempId` original de la operación), así que ningún cuboid generado -- por el mock o por Claude real -- termina llamándose literalmente así. Fix: el mock extrae por regex el id REAL del primer cuboid del `userPrompt` (que ya incluye el modelo actual serializado) cuando el modelo no contiene el fixture literal de 031 -- preserva el comportamiento exacto de los tests existentes (031/025) y funciona contra cualquier modelo real.
3. `FmmCompatibilityValidator` (013) asumía SIEMPRE la forma v5 de `outliner` (groups separados en `groups[]`) -- nunca se había corrido contra la salida de `BBModelExporterV4` (014, groups embebidos directo en el outliner), así que cada bone de un v4 real disparaba un falso `OUTLINER_REFERENCE` ("no existe en 'groups'"). Fix: mismo criterio de detección (¿tiene `name` inline?) ya usado en el parser test-only de 012.
4. `docker/docker-compose.yml` fijaba el puerto de host de MinIO (9000/9001, ticket 023/024) -- confirmado libre en la Mac de Marco, pero NUNCA antes exercitado en un agente de CI COMPARTIDO: el primer PR real de esta suite falló en Jenkins con `port is already allocated` (otro job ya lo tenía tomado). Postgres ya había resuelto este mismo problema desde el ticket 003 (puerto de host aleatorio + Spring lo autodetecta) -- MinIO nunca recibió el mismo tratamiento porque `spring-boot-docker-compose` no tiene un connector nativo para S3. Fix: `MINIO_HOST_PORT`/`MINIO_CONSOLE_HOST_PORT` (override de Compose, default 9000/9001 -- cero cambio para cualquiera que no los seteé) + `GALGOTH_STORAGE_MINIO_ENDPOINT` (relaxed binding en `application.properties`, mismo patrón que `AI_VISION_PROVIDER`/etc.) -- `scripts/e2e.sh` pasa `MINIO_HOST_PORT=0` (puerto libre elegido por Docker) y descubre el real antes de levantar el backend.

**Tests**: 219 backend (+3: `E2eAcceptanceBbmodelExportTest`, más 2 nuevos en `MockReasoningProviderTest`/`GeometryPlannerServiceTest` cubriendo los hallazgos #1/#2) + 1 test Playwright real (flujo completo, verificado corriendo 3 veces localmente contra el stack real, reproducible). `npm run lint`/`vue-tsc -b`/`npm run build`/`npm run test` (Vitest) sin tocar -- ningún cambio en esos.

**AC #3 (CI) -- NO logrado. Documentado honestamente como gap real de infra, no oculto, tras 6 rondas reales de CI y 5 hallazgos resueltos uno por uno:**
1. `npx playwright install --with-deps chromium` falló (`su: Authentication failure`) -- el agente no tiene sudo/root, necesario para que Playwright instale las librerías de sistema vía `apt`. Fix: sin `--with-deps` (solo descarga el binario del navegador).
2. `docker compose up` falló (`port is already allocated`) -- el puerto fijo 9000 de MinIO (ticket 023/024) ya estaba tomado por otro job en el agente compartido. Fix: puerto dinámico + descubrimiento (ver hallazgo #4 de la sección de arriba).
3. Con el navegador instalado y el stack real arriba, Chromium no podía LANZARSE (`libglib-2.0.so.0: cannot open shared object file`, sin root para instalarla). Se le presentó la situación al PO -- confirmó intentar un agente Docker con Playwright preinstalado antes de escalarlo como cambio de infra mayor sobre `platform`. Fix: `scripts/e2e.sh` se partió en `e2e-up.sh`/`e2e-down.sh` para que el paso que toca Chromium corra en un contenedor `mcr.microsoft.com/playwright:v1.63.0-noble` (Chromium+dependencias ya resueltas). Confirmado real: Chromium SÍ lanzó ahí.
4. **De red**: `--network host` en el contenedor de Playwright no alcanzó -- `page.goto` daba `ERR_CONNECTION_REFUSED`. Causa real: el agente de Jenkins corre DENTRO de un contenedor (Docker-outside-of-Docker) -- `docker.image().inside()` levanta un contenedor HERMANO, y `--network host` lo conecta a la red de la VM real, nunca al namespace del contenedor del AGENTE. Fix: `--network container:<id del contenedor del agente>` (mismo namespace exacto, el id vía `hostname`) -- con esto Chromium SÍ vio el frontend completo (página cargó, accessibility tree completo capturado en el trace).
5. **El hallazgo que NO se pudo resolver, tras un intento acotado adicional (decisión explícita del PO de detenerse ahí)**: con la red ya compartiendo namespace, el preflight CORS del navegador hacia el backend (`OPTIONS /api/projects`) vuelve sin ninguna cabecera (`blocked by CORS policy: no Access-Control-Allow-Origin header`) -- confirmado leyendo el trace de Playwright directamente (network log + console errors), no adivinado. Se hizo explícito el CORS del backend (`allowedHeaders("*")`, `OPTIONS` en `allowedMethods`, antes implícitos vía el manejo automático de Spring) -- MISMO resultado. Nunca reproducido en desarrollo local (mismo código, misma config CORS, docenas de verificaciones en vivo esta sesión) -- apunta a algo específico de la topología de red Docker-outside-of-Docker del agente (quizás un proxy/firewall intermedio en el namespace compartido interceptando el preflight), no a un bug de la app. **Se le presentó la situación al PO explícitamente; decidió detener la iteración de CI a ciegas acá** en vez de seguir adivinando contra un entorno sin acceso directo de diagnóstico.

**Decisión final sobre el `Jenkinsfile`, explícita, no un parche silencioso**: la etapa de CI se REMOVIÓ del pipeline compartido (`corePipeline`) -- dejarla habría bloqueado el CI de TODOS los PRs futuros del proyecto con un fallo de infra ajeno al código de cada PR. El `Jenkinsfile` documenta el gap completo en su propio comentario de cabecera, con el mismo criterio ya establecido para el gap de Sonar del ticket 008 (real, documentado, sin ocultar, pendiente de una decisión de `platform`). Uso real de la suite: `./scripts/e2e.sh` local, verificado reproducible en verde múltiples veces contra el stack real completo.

**Hallazgo real de proceso, encontrado escribiendo `scripts/e2e.sh`**: matar el PID de un `npm run dev`/`gradlew bootRun` lanzado en background (`comando &`) NO mata el proceso real (`vite`/`java`) que abrió el puerto -- npm/gradle lo lanzan como hijo, y el kill al wrapper no se propaga. Confirmado real: dos procesos `vite` quedaron vivos después de que el script reportara "limpieza OK". Fix: además del kill por PID, `lsof -tiTCP:<puerto> | xargs kill` como red de seguridad explícita en el cleanup -- verificado con múltiples corridas seguidas, siempre limpio.

**Estado real del Gate M6**: el AC #3 original de este ticket ataba "Technical Alpha completo" a que la suite reportara verde EN CI -- eso no se logró técnicamente (ver diagnóstico arriba). Los otros 32 tickets originales + el ticket 034 insertado están en `done/`, y el flujo E2E completo está genuinamente automatizado y verificado (local, reproducible) por primera vez en el proyecto. **Decisión explícita del PO (2026-09-09): el gap de CI se acepta como riesgo conocido y el Gate M6 de la épica 009 se da por cumplido con esta salvedad documentada** -- no se declara "CI verde" en falso; se declara "verificado en verde localmente, con el gap de CI en el agente compartido aceptado explícitamente, no resuelto". Technical Alpha (Fase 1 + Fase 2) queda así completo.
