# 020 — Draft persistence + autosave dirty-check + Guardar

**Milestone:** M2 · **Depende de:** 019, 003 · **HUs:** HU-08, HU-09, HU-22 · **Épica:** 015

## Objetivo
Nace de `docs/definiciones/galgoth-studio-mvp.md` (Diseño técnico §4 y HU-22 — contrato Command/Draft/Revision). Implementar la API/backend mínima para:
- persistir `mob_drafts` (autosave debounced),
- obtener el draft actual de un mob,
- incrementar `draft_version` **únicamente** cuando el contenido cambia materialmente (dirty flag/hash/versión local — detalle de implementación libre),
- crear una `mob_revision` mediante la acción explícita "Guardar" (snapshot completo e inmutable).

## Criterios de aceptación (TDD)
- Dado que el usuario deja de interactuar unos segundos y el contenido cambió materialmente desde el último draft persistido, cuando el autosave dispara, entonces `PATCH`/equivalente persiste `mob_drafts.draft_model_jsonb` e incrementa `draft_version` en 1.
- Dado que el autosave dispara pero el contenido es idéntico al último persistido, cuando corre, entonces no se escribe nada y `draft_version` no se incrementa.
- Dado un `GET` del draft de un mob que aún no tiene ninguno, cuando se consulta, entonces responde de forma explícita que no existe (no un draft vacío implícito) — mob nuevo: `current_revision_number=0`, sin fila en `mob_drafts`.
- Dado clic en "Guardar", cuando se confirma, entonces se valida el draft actual y se crea una nueva fila inmutable en `mob_revisions` con `revision_number` incrementado, actualizando `mobs.current_revision_number`.
- Dado que no hay cambios desde la última revisión guardada, cuando se intenta "Guardar", entonces la acción está deshabilitada o no genera una revisión duplicada.
- Dado que el draft falla la validación de invariantes al guardar, cuando ocurre, entonces no se crea la revisión y se retornan los errores específicos.

## Hecho

**Alcance acordado con el Product Owner (VoBo explícito vía `AskUserQuestion`, 2026-09-08):** este ticket es backend-only. El Gate M2 de la épica 015 pide literalmente "cargado el sample Carcomido vía el harness (008), se agranda una mano y se presiona Guardar → se crea una revisión", pero el harness no tiene forma de tener un `mobId` real sin la creación de mobs (CRUD, ticket 021, que no existe todavía). Se optó explícitamente por implementar y probar a fondo el backend con Testcontainers, dejando el harness sin cambios -- el Gate M2 queda demostrado a nivel de API real (no simulado), y se termina de conectar a una pantalla real cuando el ticket 021 exista.

Implementado en `backend/src/main/java/com/galgothstudio/backend/`:

- **`modelvalidation/MobProjectModelValidator`** (paquete nuevo): valida un `MobProjectModel` contra `contracts/schemas/mob-project-model.schema.json` -- primera vez que esta validación (existente desde el ticket 004 solo en tests) se invoca desde código de producción. El schema se empaqueta al classpath del backend vía un `processResources` nuevo en `build.gradle` (copia real de `contracts/schemas/`, nunca una copia a mano que pueda desincronizarse) -- antes de este ticket, la única forma de leerlo era una ruta relativa `../contracts/schemas/...` que solo funciona desde el working directory de Gradle, nunca desde un JAR desplegado.
- **`project/persistence/`** (paquete nuevo): `MobEntity`/`MobDraftEntity`/`MobRevisionEntity` (JPA, mapean las tablas ya existentes del ticket 003) + sus repositorios Spring Data. `modelJson` se guarda como `String` con `@JdbcTypeCode(SqlTypes.JSON)` -- Hibernate lo trata como JSON ya serializado y lo escribe tal cual en la columna `jsonb`, sin pasar por su propio ObjectMapper interno (que no conocería los módulos Vec3/Vec4). La conversión Java↔JSON vive en el servicio, no en las entidades.
- **`project/draft/DraftPersistenceService`**: implementa el ciclo Command → Draft → Revision.
  - `autosave()`: dirty-check por **igualdad estructural real** de `MobProjectModel` (records con `equals()` de valor correcto desde el ticket 004 -- Vec3/Vec4 ya resuelven el problema de `double[]`/identidad -- sin necesidad de comparar texto JSON). Si el contenido es idéntico al ya persistido, no se escribe absolutamente nada (verificado con `updated_at` sin cambiar, no solo `draft_version`). Sin validación de invariantes -- deliberado, coincide con el diseño (`docs/definiciones/galgoth-studio-mvp.md` solo lista Guardar/Apply/export como puntos de validación).
  - `saveRevision()` (Guardar): SÍ valida contra el JSON Schema (rechaza con detalles si falla, sin crear nada). Compara contra la revisión actual (`mobs.current_revision_number`) para no duplicar si no hay cambios reales. **Decisión de diseño no explícita en el AC**: Guardar NO toca `mob_drafts` -- ningún AC de HU-09/HU-22 lo pide, son dos propósitos independientes (resumición vs. historial inmutable), y el siguiente autosave los realinea solo.
- **`project/api/MobDraftController`** + `ApiExceptionHandler` (primer controlador REST del proyecto, establece la convención de error uniforme `{error, message, details}` para 021+): `GET`/`PATCH /api/mobs/{mobId}/draft`, `POST /api/mobs/{mobId}/revisions`. Ver `docs/API.md` para el contrato completo (status codes, formas de respuesta).
- **Tests**: 88 tests totales en backend (todos en verde) -- `MobDraftControllerTest` (11 tests, Testcontainers + MockMvc + Postgres real, uno por AC del ticket más casos de mob inexistente) y `MobProjectModelValidatorTest` (2 tests). `./gradlew test` en verde.
- **Postman**: `postman/galgoth-studio/` creado por primera vez (no existía) -- colección con los 3 endpoints + environment local.

### Hallazgos reales encontrados en el camino

- **Hallazgo arquitectónico significativo, con impacto más allá de este ticket**: Spring Boot 4.1.0 cambió su `ObjectMapper` autoconfigurado por defecto de Jackson 2 a **Jackson 3** (`tools.jackson.*`, paquete completamente nuevo). Los módulos `Vec3JacksonModule`/`Vec4JacksonModule` (ticket 004) están escritos contra la API clásica de Jackson 2 y sencillamente no se aplicaban al `ObjectMapper` que Spring MVC usa por defecto para los bodies HTTP -- el primer intento de correr `MobDraftControllerTest` falló con `NoSuchBeanDefinitionException` (no hay bean `com.fasterxml.jackson.databind.ObjectMapper`) y, tras arreglar eso, con `HttpMessageNotReadableException: Cannot deserialize Vec3 from Array`. Esto nunca se detectó antes porque ningún controlador REST existía hasta este ticket -- todos los tests previos construían su propio `ObjectMapper` a mano, sin pasar por Spring. Se resolvió definiendo explícitamente (`JacksonConfig`) un `ObjectMapper` Jackson 2 `@Primary` (con los módulos + `JavaTimeModule`, dependencia nueva `jackson-datatype-jsr310`) y un `MappingJackson2HttpMessageConverter` construido a mano a partir de él. **Esa clase está marcada `deprecated`/`for removal` en Spring Framework 7** (se suprimió la advertencia explícitamente, documentando por qué) -- es un parche funcional correcto para hoy, no la solución final. **Recomendación explícita para el Product Owner**: evaluar un ticket dedicado para migrar los módulos Vec3/Vec4 (y cualquier otro uso de Jackson 2) a la API de Jackson 3, antes de que Spring retire el soporte clásico.
- **Gotcha de testing real (no de producción), documentado en el propio test**: mezclar escrituras JPA con verificación vía `JdbcTemplate` crudo dentro de la misma transacción de test (`@Transactional`, rollback automático) NO ve los cambios recién guardados hasta forzar un `entityManager.flush()` explícito -- Hibernate difiere sus `INSERT`/`UPDATE` hasta el flush, y una transacción "participante" (la del test, no la que realmente abre la conexión) no lo dispara automáticamente al terminar cada llamada HTTP. En producción esto no aplica: el `@Transactional` del servicio SÍ es la transacción más externa en un request real, y Spring flushea/comitea al terminar.
- **Verificado manualmente contra `sonarqube-db`** (gap conocido desde el ticket 008) antes de mergear -- ver detalle de qué se encontró y corrigió en el historial de commits del PR si aplica.
