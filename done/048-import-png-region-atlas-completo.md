# 048 — Import de PNG: región seleccionada y atlas completo

**Milestone:** M8 · **Depende de:** 046, 047 · **HUs:** HU-28 · **Épica:** J (`docs/definiciones/galgoth-studio-fase3-textura.md`)

## Objetivo
Nace de `docs/definiciones/galgoth-studio-fase3-textura.md` (Diseño técnico §8, HU-28 — cierra la pregunta abierta que Fase 3 v1 había dejado pendiente). Soporta importar una imagen sobre una región UV seleccionada (con ajuste antes de confirmar) y, nuevo este ciclo, sobre el atlas completo (crop/pad seguro, NUNCA escalado — para no violar el canvas pixel-perfect ya decidido en 047).

## Criterios de aceptación (TDD)
- **(A) Región seleccionada**: dado que tengo una región UV seleccionada y pego una imagen de tamaño distinto, cuando esto ocurre, entonces se me ofrece ajustarla a las dimensiones exactas de la región antes de confirmar; al confirmar, la región queda reemplazada, registrado como un único `TexturePatchCommand` (046) acotado a esa región.
- **(B) Atlas completo, dimensiones exactas**: dado que importo un PNG cuyas dimensiones coinciden exactamente con `TextureDocument.width`/`height` vigentes, cuando lo hago, entonces se muestra una confirmación/diff (mismo patrón visual que el diff Antes/Después de IA) antes de reemplazar el atlas completo.
- **(B) Atlas completo, dimensiones distintas**: dado que importo un PNG de dimensiones distintas, cuando lo hago, entonces se me ofrece ÚNICAMENTE crop (recortar excedente) y/o pad (agregar margen transparente) — **nunca** un camino de escalado/resize, verificado explícitamente (test que confirma que no existe ninguna opción de escalar en la UI ni en el backend de esta operación).
- Dado cualquiera de los casos (A o B), cuando no confirmo explícitamente el ajuste ofrecido, entonces no se aplica nada — el atlas/región permanece sin cambios.
- Dado que confirmo un import de atlas completo (con o sin crop/pad de por medio), cuando se aplica, entonces es EXACTAMENTE UN `TexturePatchCommand` con `rect` = atlas completo — nunca múltiples comandos.
- Dado que el atlas ya está en Estado B (congelado, ver ticket 042 — existe al menos una región `PAINTED`), cuando importo un PNG de dimensiones distintas a las congeladas, entonces se aplica el mismo criterio de crop/pad hacia esas dimensiones fijas — nunca las cambia.
- Exportar la textura como PNG independiente sigue fuera de alcance — este ticket es exclusivamente sobre IMPORT (ninguna UI/endpoint de export de textura se agrega aquí).

## Hecho

Implementado end-to-end en el frontend (sin cambios de backend — ver hallazgo abajo sobre por qué no hicieron falta):

- **`frontend/src/editor/texture/textureImportTools.ts`** (nuevo, funciones puras sin canvas/DOM): `cropOrPad(source, targetWidth, targetHeight)` copia byte a byte el área superpuesta entre origen y destino, alineada a la esquina superior izquierda — recorta el excedente si el origen es más grande en un eje, rellena TRANSPARENTE (0,0,0,0) si es más chico. Nunca resamplea; el módulo no expone ninguna otra función (verificado con un test que enumera `Object.keys` del módulo). `describeImportAdjustment(sourceW, sourceH, targetW, targetH)` calcula qué crop/pad aplicaría sin tocar píxeles, para la UI.
- **`frontend/src/editor/texture/pngImportDecode.ts`** (nuevo): `decodePngFileToAtlasBuffer(file)` decodifica el PNG elegido a un `AtlasBuffer` RGBA 1:1 vía `createImageBitmap` + canvas 2D real — aislado en su propio módulo porque es el único punto de todo el flujo que depende de APIs que jsdom no implementa (mismo gotcha ya documentado por `pixelTools.ts` en 047), permitiendo testear el resto del flujo con buffers sintéticos. Libera siempre el `ImageBitmap` (`close()` en `finally`); lanza `PngDecodeError` con mensaje claro si el navegador no soporta `createImageBitmap` o si el archivo no decodifica.
- **`frontend/src/editor/texture/TextureImportPanel.vue`** (nuevo componente, montado por `TextureCanvas.vue`): reutiliza el selector de región de 047 como destino — "Todas las caras" ⇒ atlas completo (AC B), una región puntual ⇒ esa región (AC A), sin agregar un control nuevo redundante. Flujo único para ambos casos: elegir archivo → decodificar → SIEMPRE mostrar un panel de confirmación con toggle Antes/Después (mismo patrón visual que `AiEditPanel.vue`, un solo preview alternable) → sin confirmar explícitamente (Cancelar o no interactuar) nada se aplica → al confirmar, exactamente una llamada a `textureEditorStore.recordPatch(rect, before, after)` (un único `TexturePatchCommand`). El destino real (`rect`/`label`) se resuelve mediante una función (`resolveTarget`) evaluada en el momento de procesar el archivo, no como prop de valor estático — ver hallazgo de timing abajo.
- **`frontend/src/editor/texture/TextureCanvas.vue`**: agrega `TextureImportPanel` al panel de herramientas; `resolveImportTarget()` decide el destino según el selector de región ya existente.
- **Estado B (atlas congelado, 042)** satisfecho por construcción: el destino del import siempre sale del atlas/región YA vigentes — nunca se deriva un tamaño nuevo del PNG importado — verificado con un test explícito (región `PAINTED` + import de PNG de otro tamaño ⇒ el atlas conserva sus dimensiones).

**Hallazgo real, corregido durante la implementación (condición de carrera de timing de Vue)**: el primer diseño pasaba el destino como prop de VALOR (`targetRect`), calculado en `TextureCanvas.vue` a partir de `textureEditorStore.atlas`. Ese atlas se carga en el `onMounted` del padre, que corre DESPUÉS del primer montaje de sus hijos — el recómputo de props resultante (`0×0` → dimensiones reales) se aplica en un patch de Vue diferido (microtask), no de forma síncrona. Un test que dispara el import inmediatamente después de montar (sin esperar un tick) veía el snapshot `0×0` del primer render, produciendo un `TexturePatchCommand` con `rect` vacío. Corregido pasando el destino como una FUNCIÓN (`resolveTarget: () => { rect, label }`) evaluada recién al procesar el archivo — lee el estado reactivo vigente sin depender de que Vue ya haya aplicado el re-render del padre. **Propuesta de mejora continua**: es el mismo tipo de gotcha de timing de reactividad que 047 ya documentó (`triggerRef`/`watch` de un `shallowRef` de Pinia) — candidato a sumarse a la memoria de gotchas del equipo para que futuros componentes que deriven props desde un store cargado en `onMounted` lo eviten desde el diseño, en vez de descubrirlo con un test que falla.

**Decisión de implementación reportada explícitamente (el ticket no la fijaba)**: la alineación de crop/pad es esquina superior izquierda fija (el excedente se recorta por la derecha/abajo, el margen se agrega por la derecha/abajo) — la más predecible dado que el resto del editor ya usa origen superior-izquierdo (`flipY = false` en `TextureCanvas.vue`), y evita inventar un segundo eje de decisión (¿centrado?) que ni el ticket ni el Diseño técnico §8 especifican. Se aplica igual a los casos A (región) y B (atlas completo) — el AC (A) dice solo "se ofrece ajustarla" sin restringir a crop/pad explícitamente, pero el propio documento de definición (línea 28: "crop/fit de una imagen pegada a la región seleccionada") y la decisión ya aprobada de "canvas pixel-perfect sin antialiasing" (§18) hacen que escalar la región tampoco sea aceptable — se reutilizó el mismo `cropOrPad` para ambos casos en vez de introducir una segunda ruta de escalado solo para regiones. Señalado para confirmación explícita del Product Owner si la alineación/el criterio para (A) no es el esperado.

**Verificación de "nunca escalar" (AC explícito, dos capas + auditoría de backend)**: `textureImportTools.spec.ts` verifica que el módulo no exporta ninguna función de nombre relacionado a escalar/resize; `TextureImportPanel.spec.ts` verifica que ningún botón/control del panel (en los tres casos: crop, pad, exacto) ofrece esa opción, y que no existe ningún `<select>`/`<input type=range>` de "factor de escala". Sobre "ni en el backend de esta operación": no se agregó ningún endpoint nuevo para este ticket — el import ocurre 100% en memoria del lado del cliente, mismo mecanismo que Pincel/Borrador/Cubeta (047); se auditó `TextureService.upload` (045, `PUT /api/mobs/{mobId}/texture`) y confirmado que no realiza ningún resize/scale sobre los bytes recibidos (decodifica y re-codifica a PNG canónico para hashear, sin tocar dimensiones) — no hizo falta ningún cambio de backend para este ticket.

**Fuera de alcance, sin cambios (explícito en el ticket)**: exportar la textura como PNG independiente.
