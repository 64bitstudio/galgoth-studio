# 101 — Texture V2: alineamiento de coordenadas prompt↔API + `TextureGenerationPlan` por cara

## Objetivo
Nace de `docs/definiciones/anatomia-por-capas-generacion-mobs.md` (HU-6, HU-7, sección "Texture Generation V2"). La auditoría de código confirmó la causa raíz de "colores en regiones incorrectas" y "zonas en blanco": el prompt describe coordenadas para el tamaño original del sheet, pero `OpenAiImageProvider` infla la imagen real pedida a la API hasta 25x más grande — el modelo nunca puede reconciliar ambos sistemas. Este ticket corrige ese desalineamiento y formaliza `TextureGenerationPlan` (extendiendo `TexturePlan` existente) con entradas por cara que unen `cuboidId + semanticPart + face + material + atlasRegion` en un solo lugar.

**Depende de:** 099 (necesita `semanticPart` persistido). **Bloquea:** 102 (continuidad se apoya en el plan estructurado y el sistema de coordenadas ya corregido).

## Alcance
**Incluye:**
- `TextureSheetPromptComposer`: describe el grid usando las mismas dimensiones infladas que `OpenAiImageProvider` va a solicitar realmente a la API (no el tamaño original del sheet).
- `TextureSheetSlicer`: recorta usando ese mismo sistema de coordenadas consistente de punta a punta, eliminando el escalado proporcional "a ojo" actual.
- `TextureGenerationPlan` (extiende `TexturePlan`/`BoneSemanticLabel` existente): ancla a `semanticPart` persistido (en vez de reinferir desde el nombre libre del bone), y mantiene entradas por `(cuboidId, face)` que agrupan `semanticPart + material + atlasRegion` en un solo lugar — cada línea de coordenadas del prompt lleva adjunta su propia nota de material, no un bloque separado al inicio.

**No incluye:**
- Continuidad entre bones vía atlas parcial (ticket 102).
- Validación de contenido compuesto (ticket 102).
- Segmentación real por máscara bitmap — explícitamente fuera de alcance de esta iteración (ver riesgos del documento de definición: si esta corrección no basta, la iteración futura sería máscara real).

## Criterios de aceptación (TDD)
- Dado un sheet cuyo tamaño original difiere del tamaño real inflado para la API, cuando se compone el prompt, entonces el grid describe coordenadas en el sistema de la imagen real solicitada.
- Dado el resultado de la API, cuando se recorta cada cara, entonces se usa el mismo sistema de coordenadas del prompt — sin doble conversión.
- Dado un modelo con `semanticPart` ya persistido, cuando se arma el plan de textura, entonces cada entrada por cara incluye `cuboidId`, `semanticPart`, `face`, nota de material y región de atlas juntos.
- Dado el plan, cuando se compone el prompt de una sheet, entonces cada línea de coordenadas lleva adjunta su propia nota de material.
- Suite existente de `TextureSheetSlicer`/`OpenAiImageProvider` sigue en verde — no se rompe compatibilidad de formato de sheet.

## Hecho
- `ImageGenerationProvider.inflatedSheetSize(width, height)` (default identidad, `MockImageProvider` la hereda tal cual): expone el tamaño REAL que un proveedor va a pedirle a su API. `OpenAiImageProvider` la sobreescribe con el mismo algoritmo exacto que ya tenía `sizeParam` (059/060/061/063) -- `sizeParam` ahora delega en ella, ningún cambio de comportamiento HTTP (verificado: los tests HTTP existentes de `OpenAiImageProviderTest` siguen en verde sin modificarse).
- `TextureGenerationPlan` (nuevo, `aiorchestrator.texture`): una entrada por `(cuboidId, face)` que une `semanticPart` persistido (`Cuboid.semanticPart()`, ticket 099, NUNCA reinferido), la nota de material del `TexturePlan` (por `boneId`+`face`) y el `atlasUvRect` ya resuelto. `forSheet(model, texturePlan, sheet)` la construye 1:1 desde `sheet.placements()` -- `find` siempre encuentra una entrada para cualquier placement de esa misma sheet.
- `TextureSheetPromptComposer.compose` ahora recibe `(sheet, inflatedWidth, inflatedHeight, plan)`: el header describe el canvas con el tamaño REAL inflado (no `sheet.sheetWidth()/Height()`), y cada coordenada de grilla se escala por `inflatedWidth/sheetWidth` (`inflatedHeight/sheetHeight`) antes de imprimirse. Cada línea de coordenadas lleva adjunto su `semanticPart` (si existe) y su nota de material (si existe) desde el `TextureGenerationPlan` -- el bloque compartido "Notas de material: ..." del inicio del prompt ya no existe (decisión T2 del documento de definición).
- `TextureSheetSlicer.slice` ahora recibe `(bytes, sheet, inflatedWidth, inflatedHeight)`: el factor de escala usado para recortar cada `sheetRect` ya NO se infiere midiendo la imagen decodificada (`source.getWidth()/getHeight()`, el escalado "a ojo" de 065) -- se calcula desde `inflatedWidth/sheetWidth` (`inflatedHeight/sheetHeight`), el mismo valor ya conocido que alimentó el prompt. Mismo mecanismo de clipping/`RasterFormatException` sin cambios.
- `TextureGenerationService.runPipeline`: por cada sheet, pregunta `imageGenerationProvider.inflatedSheetSize(...)` UNA vez, arma el `TextureGenerationPlan` de esa sheet, y pasa ambos tanto al composer como al slicer -- un único sistema de coordenadas de punta a punta, sin doble conversión. `TextureGenerationSheetRequest` (forma fija del ticket 051) no cambió de forma -- sigue viajando con `sheet.sheetWidth()/sheetHeight()`, es el proveedor quien decide internamente cuánto inflar.
- Tests nuevos/actualizados: `TextureGenerationPlanTest` (6, nuevo -- construcción 1:1 desde la sheet, anclaje a `semanticPart` persistido, unión de nota de material por bone+face, atlasRegion sin recalcular, `find` vacío si no existe), `TextureSheetPromptComposerTest` (8, reescrito -- tamaño inflado en el header, escalado de coordenadas a distintos factores de inflado, nota de material/semanticPart por línea, falla explícito si el plan no cubre un placement de la sheet), `TextureSheetSlicerTest` (6, actualizado a la nueva firma -- el caso real del ticket 065 sigue cubierto pasando el tamaño inflado explícito en vez de dejar que el slicer lo infiera), `OpenAiImageProviderTest` (+2 tests directos sobre `inflatedSheetSize`, reutilizando el mismo `MethodSource` de invariantes que ya cubría `sizeParam` vía HTTP), `MockImageProviderTest` (+1, confirma el default identidad).
- Suite completa del backend: 548/548 en verde (0 failures, 0 errors, daemon fresco).
