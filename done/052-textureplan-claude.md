# 052 — TexturePlan vía Claude (StructuredReasoningProvider)

**Milestone:** M9 · **Depende de:** 025, 028 · **HUs:** HU-36 · **Épica:** M (`docs/definiciones/galgoth-studio-fase3-textura.md`)

## Objetivo
Nace de `docs/definiciones/galgoth-studio-fase3-textura.md` (Diseño técnico §5, punto 1). Antes de generar ninguna imagen, se necesita un análisis de material/paleta y mapeo semántico por bone a partir de la imagen de referencia ya subida en Fase 2 — vía `StructuredReasoningProvider` (Claude, ya implementado en 025), NO el proveedor de imágenes. Mismo espíritu que `ModelIntent` (028): salida estrictamente validada por schema, el flujo se detiene si la validación falla.

## Criterios de aceptación (TDD)
- Dado una imagen de referencia ya subida en Fase 2, cuando se solicita un `TexturePlan`, entonces la respuesta incluye etiqueta semántica por bone, paleta dominante/acento, y notas de material por cara.
- Dado un `TexturePlan` devuelto por el proveedor, cuando se valida contra su JSON Schema (mismo patrón que `contracts/schemas/` para `ModelIntent`), entonces una respuesta inválida detiene el flujo SIN generar ninguna imagen — mismo criterio que 028.
- Dado que se completa la llamada, cuando se persiste, entonces `ai_jobs` guarda provider/modelo/versión de prompt/versión de esquema/IDs de referencia para este paso (mismo patrón ya usado para geometría en 028).
- Dado `MockReasoningProvider` (025), cuando se usa en tests de este ticket, entonces produce un `TexturePlan` determinista reproducible — sin llamar a Claude real.

## Hecho

**Hallazgo real reportado, con VoBo dedicado pendiente del Product Owner (sin parche silencioso)**: tanto este ticket como el Diseño técnico §11 punto 1 de `docs/definiciones/galgoth-studio-fase3-textura.md` nombran `StructuredReasoningProvider`/`MockReasoningProvider` para este paso -- pero esa interfaz es puramente de TEXTO: `ReasoningRequest` (ticket 025) no tiene ningún campo de imagen (su propio Javadoc lo dice explícitamente: "sin imagen, a diferencia de VisionAnalysisRequest") y `ClaudeReasoningProvider` delega en `ClaudeMessagesClient.callWithText`, que nunca arma un content-block `image` en la llamada a Anthropic. Analizar de verdad "la imagen de referencia ya subida en Fase 2" (AC #1, literal) requiere el mismo mecanismo multimodal que ya usa `ModelIntent`/`VisionAnalysisService` (028) -- `VisionModelProvider.analyzeReferenceImage`, respaldado por `ClaudeMessagesClient.callWithImage`. Implementado con `VisionModelProvider` (y, en tests, `MockVisionProvider`) en su lugar -- es la interfaz que ya existe exactamente para "Claude mirando una imagen y devolviendo JSON estructurado". Ninguna clase de `aiorchestrator/provider/` se modificó para llegar a esta conclusión (se reutilizan tal cual, ambas ya existían desde el ticket 025) -- el único cambio es CUÁL de las dos interfaces ya existentes invoca este servicio nuevo. Si el PO prefiere una solución distinta (ej. extender `StructuredReasoningProvider` para que también acepte imagen), es un cambio de contrato de proveedor compartido que necesita su propio ticket/VoBo dedicado, no algo a decidir de paso en este.

### Implementado
- `domain/model/TexturePlan` (+ `BoneSemanticLabel`, `TexturePalette`, `FaceMaterialNote`) -- equivalente de `ModelIntent` (028) para el paso de textura. Forma elegida: `boneLabels: List<BoneSemanticLabel(boneId, boneName, semanticLabel)>` (etiqueta semántica por bone, ej. "torso", "cabeza"); `palette: TexturePalette(dominantColorHex, accentColorHex)` (colores `#RRGGBB`, GLOBAL para el `TexturePlan` completo -- es una propiedad de la imagen de concept art completa, no de una parte puntual del modelo); `materialNotes: List<FaceMaterialNote(boneId, boneName, face: FaceName, note)>` (nota de material por la combinación bone+cara, no por cuboid individual -- un bone puede tener varios cuboids y, para `TextureGenerationSheet` de 054 que genera UNA imagen coherente por bone completo, la orientación relevante es la del bone, igual que `CuboidFacePlacement.orientationHint` ya se resuelve "desde FaceName + rotación del bone" según el Diseño técnico §11). `boneId`/`boneName` viajan juntos en ambos records (evita un join contra el modelo solo para mostrar/loguear un nombre legible, mismo criterio que `TextureGenerationSheet.boneId`/`boneName` del propio Diseño técnico §11) y referencian siempre el id REAL (UUID) de un `Bone` que ya existe en el modelo -- a diferencia de `ModelIntent` (arranca de un modelo vacío, 028), este paso corre sobre un modelo con geometría de Fase 1+2 ya generada.
- `contracts/schemas/texture-plan.schema.json` (+ `contracts/fixtures/texture-plan-example.json`) -- mismo mecanismo de validación que `model-intent.schema.json`: `additionalProperties:false`, campos requeridos, `pattern` para hex (`^#[0-9a-fA-F]{6}$`) y `enum` de 6 valores para `face` (mismos nombres que `FaceName`: north/south/east/west/up/down).
- `modelvalidation/TexturePlanValidator` -- mismo patrón exacto que `ModelIntentValidator` (028): valida el árbol JSON crudo del proveedor ANTES de deserializar, mensajes de error legibles en vez de una excepción de deserialización opaca.
- `aiorchestrator/texture/TexturePlanService.analyze(imageBytes, contentType, currentModel)` -- arma el prompt (el `MobProjectModel` actual serializado completo, mismo criterio que `AiGeometryEditPlannerService`/031 para que el proveedor referencie ids reales) + la imagen, invoca `VisionModelProvider.analyzeReferenceImage`, valida contra el schema y devuelve `TexturePlanAnalysisResult(TexturePlan, AiProviderResponse)`. Una respuesta que no valida (o JSON directamente malformado) lanza `InvalidTexturePlanException` (carga la `AiProviderResponse` completa + los errores de schema, mismos campos que `InvalidModelIntentException`) -- el flujo se detiene ahí, nunca llega a construirse un `TexturePlan` ni a invocarse ningún `ImageGenerationProvider` (AC #2).
- Sin espejo TypeScript -- mismo criterio que `ModelIntent`: contrato 100% backend-a-backend (`grep` confirmó que `ModelIntent` no tiene ningún consumidor real en `frontend/src`, solo aparece como texto de un mensaje de error en un test), consumido recién por `TextureGenerationSheetPlanner` (054), sin ningún consumidor frontend hoy.
- `docs/ARQUITECTURA.md` actualizado (entrada nueva en la sección Fase 3).

### Explícitamente fuera de alcance de este ticket (no inventado, no implementado)
- **Persistencia en `ai_jobs`**: el ticket menciona el AC de persistencia, pero el `job_type`/columna `target_bone_id` nuevos para textura son diseño del ticket 054 (que todavía no existe) -- `TexturePlanAnalysisResult` ya expone los mismos 4 campos de trazabilidad (`provider`/`model`/`promptVersion`/`schemaVersion`, empaquetados en `AiProviderResponse`) para que 054 los persista tal cual, mismo mecanismo que `ModelIntentAnalysisResult` ya le da a `MobGenerationService`.
- **Cruce de que un `boneId` devuelto por el proveedor corresponda a un `Bone` real del modelo recibido**: el JSON Schema valida forma/tipos, no existencia semántica contra el modelo -- igual que el planner de geometría (028) delega esa garantía en la deserialización polimórfica de la whitelist sin revalidarla aparte. Si 054 necesita esa garantía dura, es su responsabilidad al consumir el `TexturePlan`.
- `OpenAiImageProvider`, `TextureGenerationSheetPlanner`/`TextureSheetSlicer`/`TextureCompositorService`, y el pipeline orquestador completo -- son los tickets 051/053/054, no tocados.
- **Nota de coordinación (dos agentes en paralelo)**: el ticket 051 (`OpenAiImageProvider`) corrió en paralelo en otro worktree. Sin superposición real de archivos -- 051 toca `aiorchestrator/provider/OpenAiImageProvider.java` (nuevo) y este ticket toca únicamente `aiorchestrator/texture/` (nuevo), `domain/model/TexturePlan*`, `modelvalidation/TexturePlanValidator` y `contracts/schemas|fixtures/texture-plan*` -- ningún archivo compartido modificado por ambos.
